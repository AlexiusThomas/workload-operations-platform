# Requirements Document

## Workload Operations Platform — V1

---

## Introduction

The Workload Operations Platform (WOP) is an internal web application that centralizes the management of operational workload generated by upstream systems. It tracks work items from initial intake through verified completion, reduces manual tracking overhead, prevents duplicate work claims, provides an immutable audit history, and establishes the architectural foundation for future material planning, reporting, training, quality analytics, and operational dashboards.

V1 delivers the core workload-management workflow: ingestion, assignment, execution, material runner workflow, verification, and final completion.

---

## Glossary

- **WOP**: Workload Operations Platform — the system being specified.
- **WorkPackage**: The parent operational workload unit, associated with a site, rack/position, scheduled date, and work type. A WorkPackage contains one or more WorkUnits. WorkPackage operational state is derived from the aggregate state of its child WorkUnits and MaterialRequirements wherever practical.
- **WorkUnit**: An independently executable task belonging to a WorkPackage. A WorkUnit tracks required quantity and completed quantity separately. A WorkUnit may be worked by a different worker than others in the same package.
- **MaterialRequirement**: A record of Fiber or Copper material needed by a WorkPackage or WorkUnit. Tracks material type, cable length in meters, quantity required, total meters required (length × quantity), quantity delivered, meters delivered, runner identity, WorkPackage association, timestamps, and status.
- **AuditEvent**: An immutable, append-only record of a significant user or system action.
- **ProductionEvent**: An immutable record generated only upon successful verification of a WorkUnit, used for technician production credit and reporting.
- **MaterialEvent**: An immutable record generated upon material delivery, used for Material Runner metrics (meters delivered, material runs completed, WorkPackages supplied). Separate from ProductionEvents and technician metrics.
- **WorkUnit_State**: AVAILABLE → CLAIMED → IN_PROGRESS → PREP_COMPLETE → LABELED → TOTE_ASSIGNED → READY_TO_VERIFY → VERIFIED → COMPLETE. Failed verification: READY_TO_VERIFY → REWORK_REQUIRED → IN_PROGRESS (rework path restores appropriate work state).
- **MaterialRequirement_Status**: MATERIAL_REQUIRED → MATERIAL_CLAIMED → MATERIAL_DELIVERED → READY_FOR_PREP.
- **Work_Type**: One of: Fiber, Copper, Metronome, GB200LC, GB300R, GB300AC, Prep Support, Labeling.
- **Technician**: Operational role that performs physical preparation work on WorkUnits. Claims work using a pull model.
- **Material_Runner**: Operational role responsible for delivering Fiber/Copper materials. Has a separate metrics and event model from Technicians.
- **Verifier_Lead**: Operational role with authority to verify completed work, initiate rework, and assign/reassign work as an exception.
- **Manager_Admin**: Administrative role with full read/write access, configuration authority, and exception assignment/reassignment authority.
- **Claim**: The act of a Technician atomically reserving a WorkUnit for exclusive execution using a DynamoDB conditional write.
- **Rework**: The process by which a WorkUnit that fails verification is returned to IN_PROGRESS for correction. Completed quantities and rework history are preserved.
- **Tote**: A physical container assigned to a WorkUnit before it can be submitted for verification.
- **Idempotency_Key**: A client-supplied identifier that prevents duplicate effects from repeated identical requests.
- **Rollover**: The automated process of advancing eligible AVAILABLE/unclaimed WorkUnits to the next scheduled date. Active, claimed, partial, labeled, tote-assigned, verification-pending, and rework WorkUnits are NOT silently rolled over.
- **original_scheduled_date**: The date a WorkPackage was originally scheduled, preserved immutably across rollovers.
- **current_scheduled_date**: The operative scheduled date, updated on each rollover.
- **rollover_count**: Integer counter incremented each time a WorkUnit or WorkPackage rolls over.
- **INTERNAL-INTEGRATION-TODO**: A placeholder identifying a required internal system dependency whose owner, documentation, or approval has not yet been confirmed.
- **Harmony Console**: Current candidate frontend hosting platform. Unconfirmed — tagged INTERNAL-INTEGRATION-TODO until internally validated.
- **Midway**: Current candidate internal authentication mechanism. Unconfirmed — tagged INTERNAL-INTEGRATION-TODO until internally validated.

## Requirements

### FR-001: Workload Ingestion

**User Story:** As a Manager_Admin, I want to ingest workload data from upstream systems so that WorkPackages and WorkUnits are available for scheduling and assignment.

#### Acceptance Criteria

1. WHEN a valid workload file is uploaded to the designated Amazon S3 import prefix, THE WOP SHALL parse the file and create the corresponding WorkPackage and WorkUnit records in the operational datastore.
2. WHEN a workload file is processed successfully, THE WOP SHALL transition each created WorkPackage to the IMPORTED state and emit an AuditEvent recording the ingestion.
3. IF a workload file contains a record with a WorkPackage identifier that already exists, THEN THE WOP SHALL treat the operation as a no-op for that record and emit an AuditEvent noting the duplicate.
4. IF a workload file is malformed or fails schema validation, THEN THE WOP SHALL move the file to a designated error prefix in Amazon S3 and emit an AuditEvent describing the validation failure.
5. THE WOP SHALL support idempotent ingestion so that reprocessing the same file produces no additional WorkPackage or WorkUnit records, no duplicate AuditEvents, and no additional operational credit.
6. WHEN ingestion is triggered by an Amazon EventBridge schedule, THE WOP SHALL complete the ingestion attempt within 5 minutes of the scheduled trigger time.
7. IF an ingestion Lambda fails mid-processing, THEN THE WOP SHALL not leave partially ingested WorkPackages in the AVAILABLE state; partial ingestion SHALL remain in IMPORTED or be moved to an error state with an AuditEvent.

---

### FR-002: WorkPackage and WorkUnit Creation

**User Story:** As a Manager_Admin, I want WorkPackages and WorkUnits to be created with all required attributes so that the workload is fully described before it enters the operational queue.

#### Acceptance Criteria

1. THE WOP SHALL associate each WorkPackage with a site identifier, rack/position identifier, original_scheduled_date, current_scheduled_date (initially equal to original_scheduled_date), rollover_count (initially zero), and Work_Type.
2. THE WOP SHALL associate each WorkUnit with its parent WorkPackage, a required quantity, an initial completed quantity of zero, and a Work_Type.
3. THE WOP SHALL enforce that required quantity is a positive integer and completed quantity is a non-negative integer not exceeding required quantity.
4. IF a WorkPackage creation request omits any mandatory attribute, THEN THE WOP SHALL return a validation error without creating the record.
5. THE WOP SHALL assign a system-generated unique identifier to each WorkPackage and each WorkUnit at creation time.
6. WHEN a WorkPackage and its constituent WorkUnits are created, THE WOP SHALL emit one AuditEvent per created entity.

---

### FR-003: MaterialRequirement Management

**User Story:** As a Manager_Admin or system, I want MaterialRequirements to be recorded against WorkPackages and WorkUnits so that Fiber and Copper material needs are fully tracked from requirement through delivery.

#### Acceptance Criteria

1. THE WOP SHALL allow one or more MaterialRequirements to be associated with a WorkPackage or a WorkUnit.
2. THE WOP SHALL record for each MaterialRequirement: material type (Fiber or Copper), cable length in meters, quantity required, total meters required (calculated as cable length × quantity required), quantity delivered (initially zero), meters delivered (initially zero), runner identity (initially null), WorkPackage identifier, timestamps (created_at, last_updated_at), and status (initially MATERIAL_REQUIRED).
3. THE WOP SHALL calculate and persist total meters required as cable length multiplied by quantity required at creation time.
4. IF a MaterialRequirement specifies a non-positive quantity required or a non-positive cable length, THEN THE WOP SHALL return a validation error without creating the record.
5. THE WOP SHALL allow MaterialRequirements to be read by any authenticated user with at minimum the Technician role.
6. THE WOP SHALL transition MaterialRequirement status through: MATERIAL_REQUIRED → MATERIAL_CLAIMED → MATERIAL_DELIVERED → READY_FOR_PREP.
7. WHEN a MaterialRequirement transitions to MATERIAL_DELIVERED, THE WOP SHALL persist quantity delivered, meters delivered, and the authenticated runner identity.
8. WHEN a MaterialRequirement transitions to MATERIAL_DELIVERED, THE WOP SHALL generate an immutable MaterialEvent recording: WorkPackage identifier, WorkUnit identifier (if applicable), material type, cable length, quantity delivered, meters delivered, runner identity, and ISO-8601 timestamp.

---

### FR-004: Material Runner Workflow

**User Story:** As a Material_Runner, I want to claim and deliver materials for WorkPackages so that Technicians have the materials they need to begin prep work, and my delivery activity is tracked separately from technician production metrics.

#### Acceptance Criteria

1. WHEN a Material_Runner submits a material-claim request for a MaterialRequirement in the MATERIAL_REQUIRED state, THE WOP SHALL atomically transition that MaterialRequirement to MATERIAL_CLAIMED and record the runner's server-verified identity.
2. WHEN two concurrent material-claim requests target the same MaterialRequirement, THE WOP SHALL honor exactly one claim and return a conflict error to the other requestor.
3. IF a material-claim request targets a MaterialRequirement not in the MATERIAL_REQUIRED state, THEN THE WOP SHALL return an error indicating the current status without modifying the record.
4. WHEN a Material_Runner submits a delivery confirmation for a MaterialRequirement in the MATERIAL_CLAIMED state, THE WOP SHALL transition the MaterialRequirement to MATERIAL_DELIVERED, persist quantity delivered and meters delivered, record the runner identity from server-side session context, and emit both an AuditEvent and a MaterialEvent.
5. WHEN a MaterialRequirement transitions to MATERIAL_DELIVERED, THE WOP SHALL evaluate whether all MaterialRequirements for the associated WorkPackage/WorkUnit have been delivered, and if so, automatically transition the MaterialRequirement status to READY_FOR_PREP.
6. THE WOP SHALL track the following Material Runner metrics via immutable MaterialEvents only: meters delivered, material runs completed (count of MATERIAL_DELIVERED transitions), and WorkPackages supplied (count of distinct WorkPackage identifiers in MaterialEvents for the runner).
7. Material Runner metrics (meters delivered, runs completed, WorkPackages supplied) MUST be derived exclusively from MaterialEvents and MUST NOT be combined with technician ProductionEvent metrics into a single productivity score.
8. WHEN a material-claim succeeds, THE WOP SHALL emit an AuditEvent recording the runner identity, MaterialRequirement identifier, and timestamp.
9. THE WOP SHALL reject any material-claim or delivery request in which the runner identity is supplied solely by the frontend; identity MUST be resolved from server-side session context.
10. IF a material-claim request is submitted by a user without the Material_Runner or Manager_Admin role, THEN THE WOP SHALL return an authorization error.

---

### FR-005: Workload Queue

**User Story:** As a Technician, I want to view a filtered queue of available WorkUnits so that I can identify and select work appropriate for my site and work type.

#### Acceptance Criteria

1. THE WOP SHALL present a workload queue that lists WorkUnits in the AVAILABLE state.
2. THE WOP SHALL support filtering the queue by site, Work_Type, and current_scheduled_date.
3. WHEN a Technician queries the queue, THE WOP SHALL return results within 3 seconds under normal load.
4. THE WOP SHALL display for each WorkUnit: parent WorkPackage identifier, site, rack/position, current_scheduled_date, original_scheduled_date, rollover_count, Work_Type, required quantity, and completed quantity.
5. THE WOP SHALL paginate queue results and return no more than 100 WorkUnits per page.

### FR-006: Claiming a WorkUnit (Atomic Claim — Technician Pull Model)

**User Story:** As a Technician, I want to claim a WorkUnit so that I have exclusive ownership before beginning work, and no other worker can claim the same unit simultaneously.

#### Acceptance Criteria

1. WHEN a Technician submits a claim request for a WorkUnit in the AVAILABLE state, THE WOP SHALL atomically transition that WorkUnit to the CLAIMED state and record the claiming Technician's server-verified identity.
2. WHEN two concurrent claim requests target the same WorkUnit, THE WOP SHALL honor exactly one claim and return a conflict error to the other requestor.
3. IF a claim request targets a WorkUnit that is not in the AVAILABLE state, THEN THE WOP SHALL return an error indicating the current state without modifying the WorkUnit.
4. WHEN a claim succeeds, THE WOP SHALL emit an AuditEvent recording the Technician identity, WorkUnit identifier, and timestamp.
5. THE WOP SHALL implement the atomic claim using a DynamoDB conditional write with a well-distributed WorkUnit primary key. Write sharding or additional partition mitigation MUST NOT be introduced without evidence of a real hot-key problem from concurrency and load testing.
6. THE WOP SHALL reject any claim request in which the Technician identity is supplied solely by the frontend; identity MUST be resolved from server-side session context.
7. V1 uses a technician pull model: eligible Technicians claim AVAILABLE WorkUnits by self-selection. Verifier_Lead and Manager_Admin roles MAY explicitly assign or reassign WorkUnits as an authorized exception.

---

### FR-007: Lead/Admin Assignment and Reassignment

**User Story:** As a Verifier_Lead or Manager_Admin, I want to explicitly assign or reassign a WorkUnit to a specific Technician as an authorized exception so that scheduling exceptions can be handled without disrupting the normal pull model.

#### Acceptance Criteria

1. WHEN a Verifier_Lead or Manager_Admin submits an assignment request targeting a WorkUnit in the AVAILABLE or CLAIMED state, THE WOP SHALL atomically update the assigned Technician identity and set the WorkUnit to CLAIMED.
2. IF the WorkUnit is in the CLAIMED state and is being reassigned, THE WOP SHALL emit an AuditEvent recording both the previous claimant and the new assignee, along with the Manager/Lead identity.
3. IF an assignment request is submitted by a user without the Verifier_Lead or Manager_Admin role, THEN THE WOP SHALL return an authorization error.
4. WHEN an assignment or reassignment is performed, THE WOP SHALL emit an AuditEvent recording the assigning user identity, target Technician identity, WorkUnit identifier, and timestamp.

---

### FR-008: Starting Work

**User Story:** As a Technician, I want to start work on a claimed WorkUnit so that the system reflects that active work is underway.

#### Acceptance Criteria

1. WHEN a Technician who owns the claim on a WorkUnit submits a start-work request, THE WOP SHALL transition the WorkUnit from CLAIMED to IN_PROGRESS.
2. IF a start-work request is submitted by a Technician who does not own the claim, THEN THE WOP SHALL return an authorization error without modifying the WorkUnit.
3. IF a start-work request targets a WorkUnit not in the CLAIMED state, THEN THE WOP SHALL return an error indicating the current state.
4. WHEN work is started, THE WOP SHALL emit an AuditEvent recording the Technician identity, WorkUnit identifier, and timestamp.

---

### FR-009: Partial Completion and Quantity Tracking

**User Story:** As a Technician, I want to record progress against a WorkUnit's required quantity so that partial work is preserved and not lost if I need to stop before full completion.

#### Acceptance Criteria

1. WHILE a WorkUnit is in the IN_PROGRESS state, THE WOP SHALL accept quantity update requests from the owning Technician and persist the updated completed quantity.
2. THE WOP SHALL enforce that updated completed quantity does not exceed required quantity.
3. IF a quantity update request specifies a completed quantity greater than required quantity, THEN THE WOP SHALL return a validation error without modifying the WorkUnit.
4. WHEN completed quantity is updated, THE WOP SHALL emit an AuditEvent recording the previous quantity, the new quantity, the Technician identity, and the timestamp.
5. THE WOP SHALL preserve all previously recorded completed quantity when a WorkUnit transitions to REWORK_REQUIRED and back to IN_PROGRESS.

---

### FR-010: Prep Completion

**User Story:** As a Technician, I want to mark a WorkUnit as preparation complete so that it moves to the next workflow stage.

#### Acceptance Criteria

1. WHEN a Technician submits a prep-complete request for a WorkUnit in the IN_PROGRESS state with completed quantity equal to required quantity, THE WOP SHALL transition the WorkUnit to PREP_COMPLETE.
2. IF a prep-complete request is submitted for a WorkUnit where completed quantity is less than required quantity, THEN THE WOP SHALL return a validation error indicating insufficient completion.
3. IF a prep-complete request is submitted by a Technician who does not own the claim, THEN THE WOP SHALL return an authorization error.
4. WHEN prep completion is recorded, THE WOP SHALL emit an AuditEvent recording the Technician identity, WorkUnit identifier, and timestamp.

---

### FR-011: Labeling

**User Story:** As a Technician or Verifier_Lead, I want to mark a WorkUnit as labeled so that physical labeling is tracked as a discrete step in the workflow.

#### Acceptance Criteria

1. WHEN an authorized user submits a label request for a WorkUnit in the PREP_COMPLETE state, THE WOP SHALL transition the WorkUnit to LABELED.
2. IF a label request targets a WorkUnit not in the PREP_COMPLETE state, THEN THE WOP SHALL return an error indicating the current state.
3. WHEN labeling is recorded, THE WOP SHALL emit an AuditEvent recording the user identity, WorkUnit identifier, and timestamp.

---

### FR-012: Tote Assignment

**User Story:** As a Technician or Verifier_Lead, I want to assign a tote to a WorkUnit so that physical container tracking is complete before verification.

#### Acceptance Criteria

1. WHEN an authorized user submits a tote-assignment request for a WorkUnit in the LABELED state, THE WOP SHALL persist the tote identifier and transition the WorkUnit to TOTE_ASSIGNED.
2. THE WOP SHALL require the tote identifier to be a non-empty string.
3. IF a tote-assignment request targets a WorkUnit not in the LABELED state, THEN THE WOP SHALL return an error indicating the current state.
4. WHEN a tote is assigned, THE WOP SHALL emit an AuditEvent recording the tote identifier, user identity, WorkUnit identifier, and timestamp.
5. THE WOP SHALL prevent a WorkUnit from transitioning to READY_TO_VERIFY unless a tote identifier has been recorded.

---

### FR-013: Ready-to-Verify Submission

**User Story:** As a Technician or Verifier_Lead, I want to mark a WorkUnit as ready for verification so that the Verifier_Lead knows the work is awaiting review.

#### Acceptance Criteria

1. WHEN an authorized user submits a ready-to-verify request for a WorkUnit in the TOTE_ASSIGNED state, THE WOP SHALL transition the WorkUnit to READY_TO_VERIFY.
2. IF a ready-to-verify request targets a WorkUnit that does not have a tote identifier recorded, THEN THE WOP SHALL return a validation error.
3. WHEN the WorkUnit transitions to READY_TO_VERIFY, THE WOP SHALL emit an AuditEvent recording the user identity, WorkUnit identifier, and timestamp.

---

### FR-014: Verification

**User Story:** As a Verifier_Lead, I want to verify a completed WorkUnit so that production credit is accurately awarded for work that meets quality standards.

#### Acceptance Criteria

1. WHEN a Verifier_Lead submits a verification-pass request for a WorkUnit in the READY_TO_VERIFY state, THE WOP SHALL transition the WorkUnit to VERIFIED.
2. WHEN a WorkUnit transitions to VERIFIED, THE WOP SHALL create an immutable ProductionEvent recording: WorkUnit identifier, WorkPackage identifier, Verifier_Lead identity, completed quantity, Work_Type, site, rack/position, and ISO-8601 timestamp.
3. WHEN a WorkUnit is verified, THE WOP SHALL emit an AuditEvent recording the Verifier_Lead identity, WorkUnit identifier, and timestamp.
4. IF a verification request is submitted by a user without the Verifier_Lead or Manager_Admin role, THEN THE WOP SHALL return an authorization error without modifying the WorkUnit.
5. ProductionEvents MUST be generated only upon successful verification. Work in PREP_COMPLETE, LABELED, TOTE_ASSIGNED, or any earlier state MUST NOT generate a ProductionEvent.

---

### FR-015: Rework

**User Story:** As a Verifier_Lead, I want to fail a WorkUnit's verification and send it back for rework so that defects are corrected before production credit is awarded.

#### Acceptance Criteria

1. WHEN a Verifier_Lead submits a verification-fail request for a WorkUnit in the READY_TO_VERIFY state, THE WOP SHALL transition the WorkUnit to REWORK_REQUIRED.
2. WHEN a WorkUnit transitions to REWORK_REQUIRED, THE WOP SHALL emit an AuditEvent recording the Verifier_Lead identity, WorkUnit identifier, failure reason, and timestamp.
3. WHEN a Technician claims a WorkUnit in the REWORK_REQUIRED state, THE WOP SHALL transition the WorkUnit to IN_PROGRESS, preserving all previously recorded completed quantity and the rework history in the AuditEvent log.
4. THE WOP SHALL preserve the full AuditEvent history including all prior failure records when a WorkUnit is reworked and re-verified.
5. IF a rework claim is submitted by a user without the Technician role, THEN THE WOP SHALL return an authorization error.

---

### FR-016: Final Completion

**User Story:** As a Verifier_Lead or Manager_Admin, I want to finalize a verified WorkUnit as complete so that the workflow is closed and the work is no longer surfaced in the active queue.

#### Acceptance Criteria

1. WHEN a Verifier_Lead or Manager_Admin submits a complete request for a WorkUnit in the VERIFIED state, THE WOP SHALL transition the WorkUnit to COMPLETE.
2. IF a complete request targets a WorkUnit not in the VERIFIED state, THEN THE WOP SHALL return an error indicating that verification is required before completion.
3. WHEN a WorkUnit transitions to COMPLETE, THE WOP SHALL emit an AuditEvent recording the user identity, WorkUnit identifier, and timestamp.
4. THE WOP SHALL exclude WorkUnits in the COMPLETE state from the active workload queue.

---

### FR-017: Immutable Audit History

**User Story:** As a Manager_Admin or Verifier_Lead, I want to view the full audit history for a WorkUnit or WorkPackage so that every action is traceable and non-repudiable.

#### Acceptance Criteria

1. THE WOP SHALL store every AuditEvent as an immutable, append-only record in the operational datastore.
2. THE WOP SHALL prevent deletion or modification of any AuditEvent through any application interface.
3. WHEN an audit history query is submitted for a WorkUnit or WorkPackage identifier, THE WOP SHALL return all associated AuditEvents in chronological order.
4. THE WOP SHALL record in each AuditEvent: entity type, entity identifier, action type, actor identity, actor role, before-state, after-state, and ISO-8601 timestamp.
5. WHEN an AuditEvent is written, THE WOP SHALL ensure the write is atomic with the state transition that triggered it, so that a partial failure cannot result in a state change without a corresponding audit record.

---

### FR-018: Authenticated Attribution

**User Story:** As a Manager_Admin, I want every action to be attributed to the authenticated user's server-verified identity so that audit records are trustworthy and cannot be spoofed by clients.

#### Acceptance Criteria

1. THE WOP SHALL resolve actor identity exclusively from server-side session context for every write operation.
2. THE WOP SHALL reject any write request in which the actor identity is absent from server-side session context.
3. IF a request includes a user identifier in the request body or query string that differs from the server-side session identity, THEN THE WOP SHALL use the server-side identity and log a warning AuditEvent.
4. THE WOP SHALL propagate the authenticated identity to all AuditEvent, ProductionEvent, and MaterialEvent records without allowing the client to override it.

---

### FR-019: Role-Based Authorization

**User Story:** As a Manager_Admin, I want access to actions and data to be governed by the user's assigned role so that users cannot perform operations outside their authority.

#### Acceptance Criteria

1. THE WOP SHALL enforce role-based access control on every API endpoint.
2. THE WOP SHALL define the following roles and permissions:
   - Technician: claim (pull model), start, update quantity, prep-complete, label, tote-assign, ready-to-verify, claim rework
   - Material_Runner: view queue, view MaterialRequirements, material-claim, material-deliver
   - Verifier_Lead: all Technician permissions plus verify, fail-verify, complete, assign/reassign (exception)
   - Manager_Admin: all Verifier_Lead permissions plus ingest, create, configure, read audit history, assign/reassign (exception)
3. IF a request is made to an endpoint for which the authenticated user's role lacks permission, THEN THE WOP SHALL return an HTTP 403 response without executing the requested action.
4. THE WOP SHALL evaluate role permissions server-side and SHALL NOT rely on client-supplied role claims.

---

### FR-020: Idempotent Write Operations

**User Story:** As a system integrator, I want all mutating operations to be idempotent so that retried requests due to network failures do not produce duplicate records, state changes, ProductionEvents, MaterialEvents, AuditEvents, or operational credit.

#### Acceptance Criteria

1. THE WOP SHALL accept an optional Idempotency_Key header on all mutating API requests, including: state transitions (claim, start, prep-complete, label, tote-assign, ready-to-verify, verify, fail-verify, complete), material operations (material-claim, material-deliver), import/ingestion, and rollover.
2. WHEN a request is received with an Idempotency_Key that matches a previously successful request, THE WOP SHALL return the same response as the original without re-executing the operation, without creating duplicate AuditEvents, ProductionEvents, or MaterialEvents, and without applying duplicate production or runner credit.
3. THE WOP SHALL store Idempotency_Key values with a time-to-live of at least 24 hours.
4. IF two concurrent requests carry the same Idempotency_Key, THEN THE WOP SHALL execute the operation exactly once and return the result to both callers.
5. Retry of a completion operation MUST NOT generate a second ProductionEvent.
6. Retry of a material delivery MUST NOT generate a second MaterialEvent or double-count runner metrics.
7. Retry of an ingestion MUST NOT create duplicate WorkPackage or WorkUnit records.
8. Retry of a rollover MUST NOT advance current_scheduled_date or increment rollover_count more than once per scheduled rollover cycle.

---

### FR-021: WorkUnit State Lifecycle Enforcement

**User Story:** As a system operator, I want the WorkUnit state machine to be enforced server-side so that invalid transitions are impossible regardless of client behavior.

#### Acceptance Criteria

1. THE WOP SHALL enforce the following valid state transitions for WorkUnits and reject all others:
   - AVAILABLE → CLAIMED
   - CLAIMED → IN_PROGRESS
   - IN_PROGRESS → PREP_COMPLETE
   - PREP_COMPLETE → LABELED
   - LABELED → TOTE_ASSIGNED
   - TOTE_ASSIGNED → READY_TO_VERIFY
   - READY_TO_VERIFY → VERIFIED
   - READY_TO_VERIFY → REWORK_REQUIRED
   - REWORK_REQUIRED → IN_PROGRESS
   - VERIFIED → COMPLETE
2. IF a request attempts a state transition not listed above, THEN THE WOP SHALL return a validation error and leave the entity in its current state.
3. WorkPackage operational state SHALL be derived from the aggregate state of its constituent WorkUnits and MaterialRequirements wherever practical, rather than maintained as a separate independently mutable field that could conflict with child state.

---

### FR-022: Workload Rollover

**User Story:** As a Manager_Admin, I want eligible uncompleted work to automatically roll forward to the next scheduled date so that incomplete work is not silently lost, and stale active work is surfaced for Lead review.

#### Acceptance Criteria

1. WHEN the scheduled EventBridge rollover trigger fires, THE WOP SHALL advance current_scheduled_date and increment rollover_count for each eligible WorkUnit.
2. ONLY WorkUnits in the AVAILABLE state (unclaimed, not started) are eligible for automatic rollover.
3. THE WOP SHALL NOT automatically roll over WorkUnits in any of the following states: CLAIMED, IN_PROGRESS, PREP_COMPLETE, LABELED, TOTE_ASSIGNED, READY_TO_VERIFY, REWORK_REQUIRED, VERIFIED, COMPLETE.
4. THE WOP SHALL preserve completed quantities across rollovers; a WorkUnit's completed quantity SHALL NOT be reset by rollover.
5. THE WOP SHALL preserve original_scheduled_date immutably across all rollovers; only current_scheduled_date is updated.
6. WHEN a WorkUnit rolls over, THE WOP SHALL emit an AuditEvent recording the WorkUnit identifier, previous current_scheduled_date, new current_scheduled_date, and the new rollover_count.
7. THE WOP SHALL surface WorkUnits in states CLAIMED, IN_PROGRESS, PREP_COMPLETE, LABELED, TOTE_ASSIGNED, READY_TO_VERIFY, or REWORK_REQUIRED that are past their current_scheduled_date as stale active work in a Lead/Admin review view.
8. Rollover MUST be idempotent: re-triggering rollover for the same cycle MUST NOT advance current_scheduled_date or increment rollover_count more than once.

---

### FR-023: Synthetic Development and Test Data

**User Story:** As a developer or tester, I want a mechanism to generate realistic synthetic data so that the application can be developed, tested, and demonstrated without requiring production data.

#### Acceptance Criteria

1. THE WOP SHALL include a data-generation utility that creates WorkPackages, WorkUnits, and MaterialRequirements using only synthetic identifiers such as SITE-A, RACK-001, TECH-001, RUNNER-001, and VERIFY-001.
2. THE Synthetic_Data_Utility SHALL support parameterized generation of configurable counts of WorkPackages and WorkUnits per Work_Type.
3. THE Synthetic_Data_Utility SHALL be executable in the development and test environments and SHALL NOT be deployable or invocable in the production environment.
4. THE WOP SHALL use synthetic user identities for all authentication during development; no real employee identifiers SHALL be required during development.

---

### FR-024: Reporting — Weekly Production Summary

**User Story:** As a Manager_Admin or Verifier_Lead, I want a weekly production summary that reconciles exactly to immutable ProductionEvents and MaterialEvents so that reported counts are auditable and trustworthy.

#### Acceptance Criteria

1. THE WOP SHALL produce a weekly production summary report covering: verified WorkUnit counts by Work_Type and site, total meters verified by material type, verified quantities by Technician, and material runs and meters delivered by Material_Runner.
2. THE WOP SHALL derive all report figures exclusively from immutable ProductionEvents and MaterialEvents; no figure SHALL be derived from mutable WorkUnit or MaterialRequirement state.
3. Technician production figures and Material Runner figures MUST appear in separate sections of the report and MUST NOT be aggregated into a combined productivity metric.
4. WHEN the report is generated for a given week, THE WOP SHALL produce consistent results if regenerated; reports are deterministic given the same underlying event records.
5. THE WOP SHALL support triggering report generation via EventBridge schedule (weekly) and via Manager_Admin on-demand API request.

## Non-Functional Requirements

---

### NFR-001: API Response Latency

**User Story:** As a Technician, I want API responses to be fast enough that operational flow is not disrupted.

#### Acceptance Criteria

1. THE WOP SHALL return responses to workload queue queries within 3 seconds at the 95th percentile under a concurrent load of 50 users.
2. THE WOP SHALL return responses to state-transition requests within 2 seconds at the 95th percentile under a concurrent load of 50 users.
3. THE WOP SHALL emit Amazon CloudWatch metrics for API latency at the p50, p95, and p99 percentiles.

---

### NFR-002: Availability

**User Story:** As an operations manager, I want the platform to be reliably available during operational shifts.

#### Acceptance Criteria

1. THE WOP SHALL target 99.5% monthly availability during defined operational hours.
2. THE WOP SHALL use AWS managed services (Lambda, DynamoDB, API Gateway) to eliminate single-instance failure modes.
3. THE WOP SHALL implement automated Amazon CloudWatch alarms that notify on-call personnel when error rates exceed 1% over a 5-minute window.

---

### NFR-003: Scalability

**User Story:** As a capacity planner, I want the platform to scale without architectural rework as workload volume grows.

#### Acceptance Criteria

1. THE WOP SHALL be designed so that compute capacity scales automatically with request volume using AWS Lambda concurrency.
2. THE WOP SHALL use Amazon DynamoDB with on-demand capacity mode so that read/write throughput scales without manual provisioning.
3. THE WOP SHALL support a minimum of 200 concurrent active users without degradation of the latency targets defined in NFR-001.

---

### NFR-004: Observability

**User Story:** As an operations engineer, I want structured logs, metrics, and traces so that incidents can be diagnosed quickly.

#### Acceptance Criteria

1. THE WOP SHALL emit structured JSON logs from all Lambda functions to Amazon CloudWatch Logs.
2. THE WOP SHALL include correlation identifiers in all log entries so that a single request can be traced across Lambda invocations.
3. WHERE AWS X-Ray tracing is supported, THE WOP SHALL enable active tracing on Lambda functions and API Gateway.
4. THE WOP SHALL emit custom CloudWatch metrics for: ingestion success/failure counts, state transition counts per transition type, claim conflict counts, material delivery counts, verification pass/fail counts, rollover counts, and report generation counts.

---

### NFR-005: Testability and Automated Testing

**User Story:** As a developer, I want comprehensive automated tests so that regressions are detected before deployment.

#### Acceptance Criteria

1. THE WOP SHALL include unit tests covering all Lambda handler logic with a minimum of 80% line coverage.
2. THE WOP SHALL include integration tests that exercise the API end-to-end using synthetic data and a local or emulated DynamoDB instance.
3. THE WOP SHALL include concurrency tests that verify atomic claim behavior (FR-006) and atomic material-claim behavior (FR-004) under simultaneous requests.
4. THE WOP SHALL include property-based tests for: state transition validation (all valid and invalid transitions), idempotency of all mutating write operations, WorkUnit quantity invariants (completed ≤ required), and rollover eligibility invariants.
5. WHEN the CI pipeline runs, THE WOP SHALL execute all automated tests and block deployment on any test failure.
6. THE WOP SHALL include a synthetic end-to-end test that covers the full workflow: workload ingestion → material requirement calculation → material claim/delivery → technician claim → partial work and quantity update → prep completion → labeling → tote assignment → verification and rework → verified production credit → weekly report generation → eligible next-day rollover. The report output MUST reconcile exactly to the immutable ProductionEvents and MaterialEvents in the synthetic test dataset.

### NFR-006: Infrastructure as Code

**User Story:** As a DevOps engineer, I want all AWS resources defined in Infrastructure as Code so that environments are reproducible and changes are auditable.

#### Acceptance Criteria

1. THE WOP SHALL define all AWS resources (Lambda functions, DynamoDB tables, API Gateway, S3 buckets, EventBridge rules, IAM roles and policies) using an Infrastructure as Code tool.
2. THE WOP SHALL support deployment to at minimum two isolated environments: development and production.
3. THE WOP SHALL store Infrastructure as Code definitions in source control alongside application code.
4. THE WOP SHALL support rollback of any infrastructure change to the previous known-good state.

---

### NFR-007: Configuration Separation

**User Story:** As a deployment engineer, I want configuration separated from code so that the same build artifact can be deployed to multiple environments.

#### Acceptance Criteria

1. THE WOP SHALL externalize all environment-specific configuration (table names, S3 bucket names, log levels, feature flags) as Lambda environment variables or AWS Systems Manager Parameter Store values.
2. THE WOP SHALL contain no hard-coded environment-specific values in application source code.
3. THE WOP SHALL fail at startup with a descriptive error if a required configuration value is absent.

---

### NFR-008: CI/CD Readiness

**User Story:** As a DevOps engineer, I want the project structure and pipeline definitions to support automated build, test, and deployment.

#### Acceptance Criteria

1. THE WOP SHALL include a CI/CD pipeline definition that builds, tests, packages, and deploys the application on each push to the main branch.
2. THE WOP SHALL produce deployment artifacts that are environment-agnostic and accept environment configuration at deploy time.
3. THE WOP SHALL include an operational runbook documenting deployment procedures, rollback steps, and common failure scenarios.

---

### NFR-009: Failure Handling

**User Story:** As an operations engineer, I want the platform to handle failures gracefully so that transient errors do not corrupt data or leave work in inconsistent states.

#### Acceptance Criteria

1. THE WOP SHALL use DynamoDB conditional writes for all state transitions so that concurrent modifications are detected and rejected rather than silently overwriting.
2. WHEN a Lambda function encounters an unhandled exception, THE WOP SHALL return a structured error response and emit a CloudWatch alarm within 5 minutes.
3. THE WOP SHALL implement idempotent retry logic for DynamoDB writes to ensure at-most-once side effects.
4. IF an ingestion Lambda fails mid-processing, THEN THE WOP SHALL not leave partially ingested WorkPackages in the AVAILABLE state; partial ingestion SHALL remain in IMPORTED or be moved to an error state with an AuditEvent.

---

### NFR-010: Future-Roadmap Extensibility

**User Story:** As an architect, I want the V1 design to accommodate V2–V6 roadmap additions without requiring a redesign of the core data model or API.

#### Acceptance Criteria

1. THE WOP SHALL design the DynamoDB data model with access patterns sufficient to support Material Runner workflow queries (V2) without requiring a table restructure. (Note: Material Runner workflow is now included in V1; this criterion applies to any V2 extensions of that workflow.)
2. THE WOP SHALL design API routes using versioned prefixes (e.g., `/v1/`) so that future versions can be added without breaking existing clients.
3. THE WOP SHALL record all ProductionEvents with sufficient detail (Work_Type, quantities, timestamps, user identities, site, rack/position) to support automated reporting aggregation (V3).
4. THE WOP SHALL record Technician identities on all WorkUnit actions to support training analytics (V4) and quality analytics (V5).
5. THE WOP SHALL record all MaterialEvents with sufficient detail (material type, meters, runner identity, WorkPackage, timestamps) to support V3 automated material reporting.

## Security Requirements

---

### SEC-001: Authentication Abstraction

**User Story:** As a security architect, I want authentication to use a well-defined abstraction so that the development environment can use synthetic users and the production environment can be switched to the approved internal identity provider without application code changes.

#### Acceptance Criteria

1. THE WOP SHALL implement authentication through a single, replaceable authentication module that the application invokes rather than calling an identity provider SDK directly from business logic.
2. THE WOP SHALL support synthetic user identities (e.g., TECH-001, VERIFY-001, RUNNER-001) in development and test environments without requiring a real identity provider.
3. THE WOP SHALL define the interface and contract of the authentication module in the design document so that integration with the approved internal employee authentication mechanism can be implemented by replacing the module.
4. THE WOP SHALL NOT invent or hard-code internal authentication API endpoints. Harmony Console and Midway are documented as current candidate frontend and authentication integrations but MUST remain tagged INTERNAL-INTEGRATION-TODO until internally validated. Any required integration point SHALL be marked INTERNAL-INTEGRATION-TODO with documented information requirements.

---

### SEC-002: Server-Side Authorization

**User Story:** As a security architect, I want all authorization decisions to be made server-side so that role enforcement cannot be bypassed by a modified client.

#### Acceptance Criteria

1. THE WOP SHALL enforce role-based access control in Lambda function code, not in API Gateway authorizer configuration alone.
2. THE WOP SHALL validate that the authenticated user's role permits the requested action before executing any state transition or data modification.
3. THE WOP SHALL return HTTP 403 for authorization failures and HTTP 401 for unauthenticated requests, with no information about the resource in the error body.

---

### SEC-003: Least Privilege IAM

**User Story:** As a security engineer, I want each Lambda function to have an IAM execution role with only the permissions it requires so that the blast radius of a compromised function is minimized.

#### Acceptance Criteria

1. THE WOP SHALL define a separate IAM execution role for each Lambda function.
2. THE WOP SHALL scope each IAM role's DynamoDB permissions to the specific table(s) and actions (GetItem, PutItem, UpdateItem, Query, etc.) the function requires.
3. THE WOP SHALL scope each IAM role's S3 permissions to the specific bucket prefixes the function requires.
4. THE WOP SHALL contain no IAM role with `*` resource permissions unless explicitly justified and documented.

---

### SEC-004: Data in Transit

**User Story:** As a security engineer, I want all data transmitted between clients and the API to be encrypted so that it cannot be intercepted.

#### Acceptance Criteria

1. THE WOP SHALL enforce HTTPS-only access on all API Gateway endpoints.
2. THE WOP SHALL configure API Gateway to reject HTTP requests (non-TLS).
3. THE WOP SHALL use TLS 1.2 or higher for all API endpoints.

---

### SEC-005: Data at Rest

**User Story:** As a security engineer, I want data at rest to be encrypted so that unauthorized access to storage does not expose operational data.

#### Acceptance Criteria

1. THE WOP SHALL enable server-side encryption on all DynamoDB tables using AWS-managed keys (AWS_OWNED_KMS).
2. THE WOP SHALL enable server-side encryption on all S3 buckets used for import and archive.
3. THE WOP SHALL block public access on all S3 buckets.

---

### SEC-006: Input Validation

**User Story:** As a security engineer, I want all API inputs to be validated before processing so that malformed or malicious inputs are rejected at the boundary.

#### Acceptance Criteria

1. THE WOP SHALL validate all API request bodies against a schema before passing them to business logic.
2. IF an API request body fails schema validation, THEN THE WOP SHALL return HTTP 400 with a structured error describing the validation failure without exposing internal stack traces.
3. THE WOP SHALL sanitize string inputs to prevent injection into DynamoDB expression attribute values.

---

### SEC-007: Audit Log Integrity

**User Story:** As a compliance officer, I want audit logs to be protected from modification so that the audit trail is trustworthy.

#### Acceptance Criteria

1. THE WOP SHALL store AuditEvents in a DynamoDB table that has no application-layer delete operation defined.
2. THE WOP SHALL configure the AuditEvent DynamoDB table with Point-in-Time Recovery (PITR) enabled.
3. THE WOP SHALL define IAM policies so that Lambda execution roles for operational APIs have PutItem on the AuditEvent table but no DeleteItem or UpdateItem permissions.

## Business Rules

| ID    | Rule |
|-------|------|
| BR-001 | A WorkUnit CANNOT be claimed by two workers simultaneously. The atomic claim MUST use a DynamoDB conditional write with a well-distributed WorkUnit primary key. Write sharding MUST NOT be introduced without measured evidence of a real hot-key problem. |
| BR-002 | Required quantity and completed quantity MUST be stored as separate attributes. |
| BR-003 | Partial work MUST preserve completed quantity across all state transitions, including REWORK_REQUIRED and back to IN_PROGRESS. |
| BR-004 | A tote identifier MUST be present before a WorkUnit can transition to READY_TO_VERIFY. |
| BR-005 | Verification by a Verifier_Lead or Manager_Admin MUST occur before a WorkUnit can transition to COMPLETE. |
| BR-006 | Failed verification MUST produce an immutable AuditEvent and MUST transition the WorkUnit to REWORK_REQUIRED. |
| BR-007 | ProductionEvents and technician production credit MUST be generated only upon successful verification. Work in PREP_COMPLETE or any earlier state MUST NOT generate a ProductionEvent. |
| BR-008 | Actor identity in all write operations MUST be resolved from server-side session context. Client-supplied user identifiers MUST NOT be the sole or authoritative source of attribution. |
| BR-009 | All state transitions are enforced server-side. The server MUST reject invalid transitions regardless of client behavior. |
| BR-010 | A WorkUnit in REWORK_REQUIRED that is reclaimed MUST carry its completed quantity and rework AuditEvent history forward. |
| BR-011 | Material Runner metrics (meters delivered, material runs completed, WorkPackages supplied) MUST be derived exclusively from immutable MaterialEvents. They MUST NOT be combined with technician ProductionEvent metrics into a combined productivity score. |
| BR-012 | Material delivery MUST record quantity delivered, meters delivered, and authenticated runner identity via server-side session context. |
| BR-013 | V1 uses a technician pull model. Technicians self-select AVAILABLE WorkUnits. Verifier_Lead and Manager_Admin MAY assign/reassign as an authorized exception only. |
| BR-014 | Only WorkUnits in the AVAILABLE state are eligible for automatic rollover. WorkUnits in CLAIMED, IN_PROGRESS, PREP_COMPLETE, LABELED, TOTE_ASSIGNED, READY_TO_VERIFY, REWORK_REQUIRED, VERIFIED, or COMPLETE states MUST NOT be automatically rolled over. |
| BR-015 | Rollover MUST preserve completed quantities, preserve original_scheduled_date, update current_scheduled_date, and increment rollover_count. Rollover MUST be idempotent per scheduled cycle. |
| BR-016 | Reports (weekly and on-demand) MUST be derived exclusively from immutable ProductionEvents and MaterialEvents. Technician and Material Runner figures MUST appear in separate sections and MUST NOT be aggregated into a combined metric. |
| BR-017 | A MaterialRequirement's total meters required MUST equal cable length multiplied by quantity required, calculated at creation and immutable thereafter. |

## Acceptance Criteria Summary

The V1 Workload Operations Platform is considered requirements-complete when:

1. All functional requirements FR-001 through FR-024 have been implemented, tested, and verified through automated tests.
2. All non-functional requirements NFR-001 through NFR-010 have been validated in the target environment (latency, availability, scalability, observability, IaC, CI/CD).
3. All security requirements SEC-001 through SEC-007 have been implemented and reviewed.
4. All business rules BR-001 through BR-017 are enforced server-side and covered by automated tests.
5. All High-priority open questions (OQ-001, OQ-002, OQ-003, OQ-009, OQ-011) are resolved before implementation of the affected components begins.
6. Synthetic data generation produces a complete representative dataset without requiring any production data.
7. The atomic WorkUnit claim (FR-006, BR-001) passes a concurrent load test demonstrating that exactly one claimant succeeds when two requests arrive simultaneously.
8. The atomic MaterialRequirement claim (FR-004) passes a concurrent load test demonstrating that exactly one runner succeeds when two requests arrive simultaneously.
9. Failed verification (FR-015) is demonstrably covered by an AuditEvent and correctly routes the WorkUnit to REWORK_REQUIRED, preserving completed quantity and rework history.
10. ProductionEvents are created only upon verified completion (FR-014, BR-007). No ProductionEvent is created for work in any earlier state.
11. MaterialEvents are created only upon material delivery (FR-004). Material Runner metrics are derived exclusively from MaterialEvents and are never combined with technician production metrics (BR-011, BR-016).
12. No hard-coded environment-specific configuration values exist in application source code (NFR-007).
13. Rollover advances only AVAILABLE WorkUnits, preserves completed quantities and original_scheduled_date, and is idempotent per cycle (FR-022, BR-014, BR-015).
14. Weekly production reports reconcile exactly to the underlying immutable ProductionEvents and MaterialEvents; no figure is derived from mutable state (FR-024, BR-016).
15. The synthetic end-to-end test (NFR-005 AC-6) passes completely, exercising: workload ingestion → material requirement calculation → material claim/delivery → technician claim → partial work → labeling → tote assignment → verification and rework → verified production credit → weekly report generation → eligible next-day rollover. The report output reconciles exactly to immutable ProductionEvents and MaterialEvents in the synthetic dataset.
16. No internal system integration (RATS, LB Magic, MICE, Harmony Console, Midway) has fabricated API calls or invented configuration. All unconfirmed integrations remain tagged INTERNAL-INTEGRATION-TODO.

## Consistency Analysis

After reviewing the requirements above for contradictions, gaps, and unresolved items that could materially affect the architecture, the following findings are noted:

### Confirmed Consistent

- **State machine**: WorkUnit lifecycle (AVAILABLE → ... → COMPLETE, with REWORK_REQUIRED loop) is fully enumerated in FR-021 and cross-referenced in FR-006 through FR-016. No conflicting transitions identified.
- **MaterialRequirement lifecycle**: MATERIAL_REQUIRED → MATERIAL_CLAIMED → MATERIAL_DELIVERED → READY_FOR_PREP is defined in FR-003/FR-004 and the Glossary. No conflicts with WorkUnit lifecycle.
- **Pull model**: Resolved via OQ-005. FR-006, FR-007, and BR-013 are mutually consistent.
- **WorkPackage state derivation**: Resolved via OQ-008. FR-021 AC-3 and the Glossary are consistent.
- **Production credit**: BR-007 (ProductionEvent only on verification), FR-014 (VERIFIED transition triggers ProductionEvent), and FR-024 (reports derived from ProductionEvents only) are mutually consistent.
- **Material Runner metrics**: BR-011, BR-016, FR-004 AC-6/7, and FR-024 AC-3 are mutually consistent. MaterialEvents are separate from ProductionEvents at the data model level.
- **Idempotency**: FR-020 covers all mutating operations identified; BR-015 covers rollover idempotency; NFR-005 AC-4 covers property-based idempotency tests.
- **Concurrency**: FR-006 AC-5 (WorkUnit claim), FR-004 AC-2 (material claim), and BR-001 specify conditional writes without premature write sharding.
- **Rollover**: FR-022 and BR-014/BR-015 are consistent. AVAILABLE-only eligibility is clear. Stale active work surfacing is included (FR-022 AC-7).
- **Audit atomicity**: FR-017 AC-5 requires AuditEvent writes to be atomic with the triggering state transition.
- **Security**: SEC-001 through SEC-007 are consistent with FR-018, FR-019, and BR-008. Authentication abstraction is correctly scoped.

### Remaining Open Items That Could Affect Architecture

1. **OQ-006 (Tote cardinality)**: If one tote can hold multiple WorkUnits, the data model must support a tote-to-WorkUnit 1:many mapping rather than a simple tote string on the WorkUnit. This affects DynamoDB access patterns and the TOTE_ASSIGNED guard in FR-012/FR-013.
2. **OQ-014 (Material claim atomicity)**: FR-004 AC-1 describes an atomic claim but does not explicitly specify a DynamoDB conditional write. If the design team determines optimistic locking is insufficient, the implementation pattern should match FR-006's conditional-write pattern. This must be resolved before the material runner data model is finalized.
3. **OQ-007 (Event retention)**: AuditEvent, ProductionEvent, and MaterialEvent retention periods are unknown. If regulatory requirements mandate long retention with separate archival, this affects DynamoDB TTL configuration and S3 archival Lambda design.
4. **OQ-010 (IaC tool)**: CDK, Terraform, SAM, and CloudFormation have different deployment models. The choice affects CI/CD pipeline design and rollback capability described in NFR-006 and NFR-008.
5. **OQ-013 (Rollover schedule)**: The rollover EventBridge rule cannot be finalized until the schedule is confirmed by operations. This is a deployment-configuration item, not an architecture blocker, but should be resolved before production deployment.
6. **DEP-001/OQ-001 (Ingestion schema)**: The S3 ingestion Lambda cannot be finalized until the upstream file format is confirmed. FR-001 is correctly gated on this.
7. **WorkPackage aggregate state computation**: FR-021 AC-3 defers the precise derivation rules to the design. The design document must specify exactly how WorkPackage state is computed from child WorkUnit states (e.g., all COMPLETE → WorkPackage COMPLETE; any REWORK_REQUIRED → WorkPackage REWORK_REQUIRED; etc.) to avoid ambiguity during implementation.

None of the above items are blockers for beginning the system design document. They are documented for resolution during design or before the affected implementation tasks begin.
